## ข้อ 1: วิเคราะห์ Bug ในส่วนที่ 2 ที่รันปกติผ่าน แต่พังใน Edge Case หรือเมื่อหลาย Thread ทำงานพร้อมกัน (ยกมา 2 ข้อ)

### กรณีที่ 1: เมธอด `concurrent_restock` (Concurrency Bug)
* **พฤติกรรม:** หากรันในกรณี Single Thread ทั่วไป เมธอดนี้จะทำงานได้ถูกต้อง 100% สต็อกจะเพิ่มขึ้นตามปกติ แต่เมื่อทำงานในสภาพแวดล้อมจริงที่มีหลาย Thread เรียกใช้งานพร้อมกัน (Multi-threading) จะเกิดปัญหา **Race Condition / Lost Update** เนื่องจากตัวแปร `current` ถูกอ่านค่าออกมาก่อนเข้าบล็อก `with self._lock:` ทำให้หลาย Thread อ่านค่าเริ่มต้นตัวเดียวกัน และเข้าคิวเขียนทับค่ากันเอง ส่งผลให้ยอดสต็อกสินค้าสูญหายไป
* **เหตุผลที่ Test ธรรมดาจับไม่เจอ:** เพราะ Unit Test มาตรฐานโดยทั่วไปถูกรันแบบตามลำดับคำสั่ง (Sequential / Single-threaded) คำสั่งจะทำงานเสร็จทีละตัว จึงไม่มีจังหวะที่เธรดจะแทรกแซงกันได้

### กรณีที่ 2: เมธอด `average_unit_value` (Edge Case Bug)
* **พฤติกรรม:** ในกรณีทดสอบทั่วไปที่มีสินค้าในคลัง ฟังก์ชันจะรันผ่านและไม่เกิด Error (แม้ตัวหารจะผิดความหมายเป็นจำนวนชนิด) แต่เมื่อเกิด **Edge Case: คลังสินค้าว่างเปล่า (`_items = {}`)** ตัวแปร `total_items` จะมีค่าเป็น 0 ทำให้เกิดข้อผิดพลาดรุนแรง `ZeroDivisionError: division by zero` และทำให้ระบบแครช
* **เหตุผลที่ Test ธรรมดาจับไม่เจอ:** เพราะชุดข้อมูลทดสอบ (Mock Data / Fixtures) ส่วนใหญ่มักเตรียมสินค้าจำลองไว้ในคลังเสมอ หากผู้เขียน Test ไม่ได้ออกแบบ Edge Case ครอบคลุมกรณีลิสต์ว่าง (Empty List Coverage) บั๊กนี้จะหลุดรอดไปสู่ Production ได้ง่าย

## ข้อ 2: ออกแบบ Test Case ที่จับ Concurrency Bug ในส่วนที่ 2 (`concurrent_restock`)

### โค้ดทดสอบด้วย Pytest และ Threading:

```python
import threading
import pytest
from inventory import Inventory
from inventory_service import InventoryService

def test_concurrent_restock_race_condition():
    """
    ทดสอบการเติมสต็อกพร้อมกัน 10 เธรด เธรดละ 10 ชิ้น
    จากสต็อกเดิม 0 ชิ้น ยอดสุดท้ายต้องได้ 100 ชิ้นพอดี
    หากมีบั๊ก Lost Update ยอดสุดท้ายจะได้น้อยกว่า 100
    """
    inv = Inventory()
    inv.add_item("สินค้าทดสอบ", 0, 50.0)
    service = InventoryService(inv)

    num_threads = 10
    amount_per_thread = 10
    threads = []

    # ฟังก์ชันเป้าหมายสำหรับให้แต่ละ Thread รัน
    def worker():
        service.concurrent_restock("สินค้าทดสอบ", amount_per_thread)

    # สร้างและสั่งเริ่มทำงาน 10 เธรดแทบจะพร้อมกัน
    for _ in range(num_threads):
        t = threading.Thread(target=worker)
        threads.append(t)
        t.start()

    # รอให้ทุกเธรดทำงานเสร็จสิ้น
    for t in threads:
        t.join()

    # ยืนยันผลลัพธ์ว่าสต็อกรวมต้องเป็น 100 ชิ้น
    actual_stock = inv._items["สินค้าทดสอบ"].quantity
    assert actual_stock == num_threads * amount_per_thread, (
        f"เกิด Race Condition! สต็อกที่คาดหวังคือ 100 แต่ได้จริงเพียง {actual_stock}"
    )
```

### คำอธิบายการจำลองการทำงานพร้อมกัน:
ต้องใช้ `threading.Thread` สร้างตัวแทนผู้ใช้งานจำลองหลายคนขึ้นมาพร้อมกัน และเรียกสั่ง `start()` ต่อเนื่องกันอย่างรวดเร็วเพื่อให้เธรดแย่งกันเข้าถึงทรัพยากรตัวแปร `quantity` จากนั้นใช้ `join()` เพื่อรอให้ทุกเธรดเสร็จสิ้นแล้วจึงตรวจสอบผลรวม หากโค้ดมีบั๊ก Lost Update ยอดที่ได้จะไม่ถึง 100 ชิ้น

## ข้อ 3: ประเมิน AI ในการ Review โค้ด และการแบ่งงานระหว่างคนกับ AI

### การประเมินความสามารถของ AI Reviewer:
1. **จุดเด่นที่ AI ทำได้ดีมาก:** 
   - ตรวจจับข้อผิดพลาดด้าน Syntax, Type Hint, และ Code Formatting (PEP 8) ได้รวดเร็ว
   - ตรวจสอบความสอดคล้องระหว่าง Docstring กับชื่อฟังก์ชัน
   - ชี้แนะการจัดการข้อยกเว้นพื้นฐาน เช่น การดัก `ZeroDivisionError` หรือตัวแปรที่อาจเป็น `None`
2. **จุดอ่อนและสิ่งที่ AI มักมองข้าม:**
   - **Concurrency & Race Conditions:** AI มักถูกหลอกเมื่อเห็นคำว่า `with self._lock:` โดยคิดว่าปลอดภัยแล้ว ทั้งที่การอ่านค่านอกล็อกทำให้เกิดช่องโหว่ Lost Update
   - **Business Logic & Atomicity:** AI มักไม่เข้าใจผลกระทบเชิงธุรกิจ เช่น การขายหลายรายการแล้วระบบไม่ Rollback ทำให้ยอดเงินหรือสต็อกค้างกลางทาง
   - **Encapsulation:** มักมองข้ามการแอบเข้าถึงตัวแปร Private (`_items`) ข้ามคลาส

### การแบ่งงาน Review ระหว่างคนกับ AI ให้ปลอดภัยที่สุด:
* **ขั้นที่ 1 (AI Pre-screening):** ให้ AI ทำหน้าที่เป็น่านแรก (First-pass review) เพื่อคัดกรอง Linting, Style, ตรวจสอบความสมบูรณ์ของ Docstring และเตือนจุดเสี่ยงพื้นฐาน
* **ขั้นที่ 2 (Human Deep Review):** ให้นักพัฒนา (Software Engineer) โฟกัสไปที่ตรรกะระดับสูง 3 ด้านสำคัญ:
  1. ความถูกต้องของสถานะระบบ (State Integrity & Rollback)
  2. การทำงานแบบขนานและความปลอดภัยของเธรด (Thread Safety & Locks)
  3. สิทธิ์การเข้าถึงข้อมูลและบริบทของโดเมนธุรกิจ (Business Domain Rules)
